01Executive Summary

YANSY TECH's platform — a bilingual (EN/AR) agency marketing site, client portal, and admin dashboard built on React 19 + Express 5 + MongoDB — was audited end-to-end ahead of its first production launch. The audit covered security, database design, API consistency, frontend/UX quality, accessibility, SEO, code quality, and deployment configuration.

Overall finding: the codebase reflects a genuinely mature build — consistent architecture, a real design system, thoughtful bilingual/RTL handling throughout, and (in several places, e.g. the public-facing focus-trap implementations and the error-handling middleware) accessibility and error-handling work that exceeds what most production codebases ship with on day one. Against that strong baseline, this audit found 2 Critical, 7 High, and 11 Medium severity issues — the large majority of which were fixed and verified live during this engagement, not just patched blind.

What this means in practice

  • Two real Insecure Direct Object Reference (IDOR) vulnerabilities and a CSRF exposure that could have let an authenticated user read/modify another user's data have been closed and verified.
  • A file-upload content-validation bypass (the "magic bytes" check was silently no-op'ing because its dependency was never installed) has been fixed — this specifically closes a stored-XSS-via-upload path.
  • An unauthenticated, cost-incurring AI chat endpoint that had no per-IP budget beyond the generic global rate limiter now has one.
  • A production nginx config had a syntax error inside its commented-out HTTPS block that would have broken nginx -t the moment SSL was enabled following the file's own instructions — fixed before it could bite on the actual go-live day.
  • The Node process had no graceful-shutdown or crash-safety handling at all — added and live-tested.
  • Several real database index gaps meant the two fastest-growing collections in the app (AI support conversations, message threads) were doing full collection scans on every admin dashboard load — fixed with verified compound indexes.

What was deliberately left as a documented recommendation, not force-fixed

  • The app has no server-side rendering, meaning social-media link previews (Facebook/X/LinkedIn/WhatsApp) will always show the homepage's title/image for any deep link — a structural limitation of the current architecture, not a quick patch.
  • 13 high-severity npm dependency vulnerabilities exist in core packages (multer, mongoose, nodemailer, axios, ws) that require breaking major-version upgrades — these need a dedicated regression-testing pass, not a same-session forced upgrade during a launch audit.
  • 143 ESLint issues remain (mostly no-unused-vars/no-empty housekeeping, some react-hooks/exhaustive-deps warnings) — real but low-urgency debt.

02Audit Method

Given the scope requested — a genuine, full-codebase professional audit rather than a surface scan — the work was structured in two phases:

Phase 1 — Independent parallel research

Four separate, independently-scoped audit passes were run in parallel, each reading actual source code (not pattern-matching) and reporting concrete file:line findings with a real exploit/failure scenario for each:

  1. Security — authentication, authorization/RBAC, IDOR, password handling, injection, rate limiting, CORS/Helmet, file upload validation, error leakage, secrets, session/cookie security, CSRF, logging.
  2. Performance / Database / API — index coverage vs. actual query shapes, N+1 patterns, pagination, .lean() usage, REST status-code and response-shape consistency, bundle size, lazy-loading, image/font strategy.
  3. Frontend / Accessibility / SEO — meta tags, Open Graph, canonical URLs, structured data, sitemap/robots, heading hierarchy, ARIA, focus management, contrast, responsive breakpoints, loading/empty/error states.
  4. Code Quality / Deployment Readiness — crash safety, graceful shutdown, compression/security headers, env var coverage, nginx/PM2/deploy configuration, dead code, duplication, ESLint health.

Phase 2 — Triage, fix, and live verification

Findings were triaged by actual severity and blast radius (not just the label an automated tool would assign). Every fix applied was verified against the running application — not merely edited and assumed correct — including:

  • End-to-end register → login → change-password → forgot-password flow testing after the User.password schema change, using temporary throwaway test accounts created and deleted for this purpose.
  • Live HTTP testing of the fixed CastError→400 mapping, the four .lean()-converted list endpoints, and the new AI-chat rate limiter.
  • A clean server boot showing the duplicate-index warning count go from 6 to 0.
  • An isolated process boot/kill test confirming the new uncaughtException handler actually fires and exits cleanly.
  • A Playwright-driven browser test confirming the new admin-dialog focus trap holds focus inside the dialog across 15 Tab presses and correctly restores focus to the trigger element on Escape.
  • Generating a real sitemap.xml with injected portfolio URLs from live database records and validating the output is well-formed XML.
  • A full npm run build and full server Jest suite run after all changes, confirming zero new build errors and zero new test regressions (154/161 tests passing; the 7 pre-existing failures were individually traced to stale assertions referencing route code that no longer exists in the current architecture — confirmed unrelated to this audit's changes).

03Security Findings

CriticalFixed & VerifiedIDOR — any authenticated user could modify/archive/pin any message thread
server/controllers/messageController.js — updateThreadStatus, archiveThread, pinThread

These three handlers had zero role or participant-ownership check, unlike sibling handlers (updateThreadPriority, assignThread) in the same file. Any logged-in customer who obtained another thread's ObjectId could close/archive/pin it. Fixed by adding the same participant-or-admin ownership check already used by getThread/getThreads; pinThread was restricted to admins only (it's an admin-inbox-triage concept with no customer-facing equivalent).

HighFixed & VerifiedIDOR — any authenticated user could attach files to any project
server/controllers/projectController.js — addFile

No ownership check before pushing arbitrary fileIds into a project's file list — a second customer account could inject file references into another customer's project. Fixed with the same ownership check getProjectById already uses.

HighFixed & VerifiedFile-upload content validation was silently no-op'ing
server/controllers/fileController.js — validateMagicBytes

The magic-byte content check dynamically imports the file-type npm package — which was never actually installed (confirmed absent from both package.json and node_modules). The catch block silently degraded to trusting the client-supplied MIME header, the exact spoofable check it was meant to replace. An HTML/SVG file with an embedded script, uploaded with Content-Type: image/png, would have passed. Fixed by installing file-type@19 and verifying it correctly distinguishes a real PNG from spoofed content.

HighFixed & VerifiedCSRF exposure via unnecessary SameSite=None cookie
server/controllers/authController.js — setTokenCookie / clearTokenCookie

The auth cookie used sameSite: 'none' in production with no CSRF token anywhere in the app. A bare cross-site form POST (which CORS does not block) would carry the cookie to any state-changing endpoint. Since the frontend (yansytech.com) and API (api.yansytech.com) are subdomains of the same registrable domain, SameSite=Lax still works correctly for legitimate cross-subdomain requests while actually blocking true cross-site CSRF. Changed to 'lax' everywhere.

HighFixed & VerifiedUnauthenticated AI chat endpoint had no dedicated cost ceiling
server/routes/ai.js — POST /chat

Deliberately public (it's the visitor-facing support widget), but its only protection was the blanket 300 req/min global limiter — real, metered LLM spend with no per-IP budget. Added a dedicated 30/hour/IP limiter scoped to this route only.

MediumFixed & VerifiedPassword hash not excluded at the schema level
server/models/User.js

Every controller currently remembers to .select('-password') — enforced by convention, not schema. Added select: false to the field itself, and updated the 4 call sites that legitimately need the hash (login, change-password, delete-account, the Google-only detection in forgot-password) to explicitly .select('+password'). Verified the full register → login → change-password → forgot-password flow end-to-end afterward.

MediumFixed & VerifiedCSV export vulnerable to formula injection
server/controllers/userController.js — exportCSV

User-controlled fields (name, company, email, phone) were only quote-escaped, not neutralized against a leading =/+/-/@ — a registered user with a formula-payload name would have it execute the moment an admin opened the export in Excel/Sheets. Added the standard OWASP mitigation (quote-prefix any cell starting with those characters) plus proper quoting of every field, which also fixes a latent unrelated bug where a comma in an email/phone value would have silently shifted every column after it.

MediumFixed & VerifiedImpersonation sessions were audit-indistinguishable from the target user's own actions
server/middleware/auth.js, server/utils/auditLogger.js

The impersonation JWT already carried an impersonatedBy field, but nothing read or propagated it — every audit-logged action taken during an impersonated session looked identical to the target user's own activity. Also removed a dead, permanently-no-op impersonation stub (checking req.user before it's ever set in the same middleware) that was actively misleading about how impersonation actually works. authenticate now propagates req.impersonatedBy, and every audit() call tags it into the log's metadata when present.

Verified secure — not just assumed

  • JWT_SECRET has no fallback/default anywhere — a missing env var fails loudly rather than silently using a guessable secret.
  • Password reset: cryptographically random token, SHA-256 hashed at rest, 1-hour expiry, single-use, and the forgot-password endpoint always returns an identical generic message regardless of whether the email exists — no user-enumeration leak (re-verified live in this audit).
  • bcrypt salt rounds = 10; account lockout after 10 failed logins for 2 hours; login/password-reset endpoints are already rate-limited.
  • Every admin route sampled correctly applies authenticate + requireAdmin/requirePermission at the router level.
  • Stripe webhook: raw body captured before the JSON parser, signature verified, idempotent via processed-event tracking.
  • CORS is an explicit allow-list (not a wildcard); Helmet is applied with a real CSP, not disabled.
  • The centralized error-handling middleware correctly gates stack traces/raw messages behind NODE_ENV and maps Mongoose error types to correct HTTP status codes.
  • No hardcoded secrets/API keys found anywhere in source; .env is gitignored.

Documented, not force-fixed this session

  • Low — The generic XSS input sanitizer (middleware/sanitize.js) uses a naive regex that misses unquoted event-handler attributes (e.g. <img onerror=...>) and the NoSQL-injection key-stripper doesn't recurse into arrays. Both are defense-in-depth layers behind other protections (CSP, parameterized Mongoose queries) — recommend replacing with a real HTML sanitizer library (e.g. sanitize-html) post-launch rather than patching the regex.
  • Medium — 13 high-severity npm audit findings in core dependencies (multer, mongoose, nodemailer, axios, ws, engine.io) all require a breaking major-version upgrade (npm audit fix --force) — deliberately not applied blind during a launch audit; needs its own regression-tested upgrade pass.

04Performance / Database / API Findings

HighFixed & VerifiedMissing compound indexes on the two fastest-growing collections
server/models/SupportConversation.js, server/models/Message.js

The admin leads-list and escalations-list queries (every AI chat conversation logs into this collection) filtered/sorted on field combinations with no supporting compound index — full collection scan + in-memory sort on every load. Same issue on the message-thread inbox (admin and customer views). Added indexes matching the actual query shapes exactly; verified via a clean server boot.

HighFixed & Verifiedportfolio.routes.js bypassed centralized error handling on all 15 routes
server/routes/portfolio.routes.js

Every handler caught errors locally and always returned a flat 500 with the raw error message — including for client-input errors like a malformed ObjectId (a Mongoose CastError), which every other resource in the API correctly maps to 400 via the central error handler. Converted all 15 handlers to next(err); live-verified the malformed-ID case now returns 400 {"error":"Invalid _id.","code":"INVALID_ID"} instead of a raw 500.

MediumFixed & VerifiedDuplicate Mongoose index declarations (boot-time warnings, wasted index builds)
Plan.js, Subscription.js, SupportConversation.js, SupportTicket.js, Feedback.js

Five models declared the same field as an index twice (once via unique:true/index:true, again via a separate schema.index() call). Removed the redundant declarations; verified boot-time duplicate-index warnings went from 6 to 0.

MediumFixed & VerifiedMissing .lean() on four hot read-only list endpoints
portfolio.routes.js (public + admin list), projectController.getAllProjects, userController.getAllUsers, messageController.getThreads

Full Mongoose document hydration for data that's only ever JSON-serialized. Added .lean() to all four; one (getThreads) required adapting a .toObject()/Map-field .get() call to the plain-object shape .lean() returns — live-tested all four endpoints afterward with real HTTP requests.

Already solid — verified, not re-litigated

  • Every list endpoint sampled has real pagination; no unbounded .find() anywhere.
  • No genuine N+1 query pattern found in any controller.
  • Route-level code splitting: literally every page (public and ~20 admin pages) is lazy()-imported in App.jsx.
  • Image handling (ProgressiveImage.jsx) already implements srcSet, responsive sizes, lazy/eager loading, blur-up placeholders, and correct fetchPriority.
  • Font loading already uses preconnect + display=swap, no render-blocking @import.
  • Production build: no single JS chunk exceeds 150kB gzipped; main entry bundle is 138kB gzipped.
  • The centralized error handler (once wired to every route) correctly maps Mongoose ValidationError/CastError/duplicate-key/JWT errors to the right HTTP status codes.

Documented, not force-fixed this session

  • Low — Sequential (not Promise.all-batched) admin-notification fan-out in projectController.js, inconsistent with the pattern used elsewhere in the same codebase. Low traffic path, low urgency.
  • Low — Pagination response shape isn't fully consistent across every admin list endpoint (page/pages vs currentPage/totalPages) — a DX/consistency nit, not a bug.

05Frontend, Accessibility & SEO Findings

CriticalArchitectural — documentedNo server-side rendering / prerendering
Pure Vite SPA, confirmed no SSR/prerender tooling anywhere in the build

Per-page meta tags are applied client-side via useSEO() — genuinely well-built for what a client-only site can do, but social crawlers (Facebook, X/Twitter, LinkedIn, WhatsApp, Slack) don't execute JavaScript, so any shared Portfolio/Case-Study/Blog/Contact link will always render the homepage's title, description, and image. This is a structural limitation of the current architecture, not something to patch in an audit pass — see Recommendations for the actual remediation path (prerendering or SSR migration).

HighFixed & VerifiedPortfolio detail pages entirely missing from sitemap.xml
client/public/sitemap.xml — was 100% static/hardcoded

Portfolio is the one content type on the site that's admin-managed/dynamic rather than a hand-authored data file — as the admin publishes new case work, none of it ever reached the sitemap. Built server/scripts/generateSitemap.js, which regenerates the portfolio-URL block from live, published DB records between two marker comments in the built sitemap.xml, wired into deploy/deploy.sh to run on every deploy. Verified: generated a real sitemap from live dev data and confirmed well-formed XML output.

HighFixed & VerifiedGlobal error fallback violated the site's own light-only, bilingual requirements
client/src/components/ErrorBoundary.jsx

The catch-all error boundary wrapping the entire app rendered a hardcoded dark-theme, English-only page on any uncaught error — directly inconsistent with the project's explicit light-only rebrand and its bilingual/RTL requirement for every component. Rewritten to match the site's actual light theme, fully bilingual via useLanguage(), with corrected text-contrast ratios (the original had two text colors failing WCAG AA against the dark background).

MediumFixed & VerifiedSystem-wide contrast token failed WCAG AA
client/src/index.css — --text-tertiary

Computed contrast ratio ~2.55:1 against white (AA minimum is 4.5:1 for normal text), used at 8–13px across 14+ files for labels/captions/microcopy. Darkened to the same hue family at ~4.7:1 — a single design-token change that fixes every call site at once.

MediumFixed & VerifiedRTL click-vs-keyboard navigation contradiction in the chat screenshot lightbox
client/src/components/reviews/ChatLightbox.jsx

Its keyboard handler correctly swapped Left/Right-arrow direction under RTL, but its click handlers did not — in Arabic mode, the Left-arrow key and clicking the physically-left button moved in opposite directions. The sibling portfolio-gallery lightbox already gets this right; applied the identical pattern here.

MediumFixed & VerifiedAdmin dialogs lacked focus trapping and focus restore
client/src/admin-ui/Modal.jsx (Modal, ConfirmDialog, Drawer)

Unlike every public-facing modal in the codebase (which all correctly trap Tab focus and restore it to the trigger on close), the shared admin dialog primitive only handled Escape — every admin dialog in the app inherited this gap. Built a shared useDialogA11y hook mirroring the established public-lightbox pattern and applied it to all three admin dialog components. Verified live via Playwright: focus correctly lands inside the dialog on open, stays trapped after 15 Tab presses, and restores to the trigger button on Escape.

MediumFixed & Verified404 page indexable by Google due to a prop-name typo
client/src/pages/NotFound.jsx

noindex: true was passed where the hook expects noIndex (React silently ignores unrecognized props) — the 404 page fell through to the default indexable behavior. One-line fix.

Already solid — verified, not re-litigated

  • Open Graph, Twitter Cards, canonical URLs, and JSON-LD structured data (Organization/ProfessionalService + per-page WebPage/FAQPage schema) are all genuinely well-implemented for a client-rendered site.
  • robots.txt is thoughtfully configured, including an explicit AI-crawler allowlist.
  • Single, correctly-nested heading hierarchy on every page sampled.
  • ProjectRequestForm.jsx (the main lead-gen form) already implements a genuine focus trap, focus restore, Escape-to-close, and properly associated form labels — better accessibility engineering than most production forms.
  • The portfolio gallery lightbox and chat-screenshot lightbox both already had real focus-trap/restore before this audit (only the RTL click-direction bug above needed fixing).
  • PortfolioSection.jsx is a model implementation of loading/empty/error state handling, including distinct copy for "failed to load" vs "no results in this filter" — the bar the rest of the app should be measured against.
  • A real, branded, bilingual 404 page exists and is correctly wired to the router catch-all.

Documented, not force-fixed this session

  • Low — LanguageSelector.jsx's dropdown uses native buttons (fully keyboard-operable) but not the idiomatic role="listbox"/arrow-key ARIA pattern.

06Code Quality & Deployment Findings

CriticalFixed & Verifiednginx production config had a syntax error inside its own commented-out HTTPS block
deploy/nginx/yansytech.com.conf

Three lines meant to be commented out were missing their # — a live, uncommented location block sitting outside any server{}. Following the file's own instruction to "uncomment after SSL is set up" would have made nginx -t reject the entire config on the actual go-live day. Fixed and verified every line in both commented HTTPS blocks is now consistently prefixed.

HighFixed & VerifiedNo process-level crash safety or graceful shutdown
server/server.js

No unhandledRejection/uncaughtException handlers and no SIGTERM/SIGINT graceful shutdown — every deploy/restart hard-killed in-flight requests and the MongoDB connection instead of draining them, and an unhandled rejection anywhere in the app previously vanished with no log line. Added all three. Live-verified: an isolated boot/kill test confirmed the uncaughtException handler fires correctly and exits cleanly (triggered naturally by a real port conflict during testing); the graceful-shutdown logic itself (HTTP server drain → Mongo close → exit) was code-verified and will engage correctly on the Linux production target via PM2's SIGTERM on restart.

MediumFixed & VerifiedDuplicated slugify implementation, three independent copies
portfolio.routes.js, clientLogos.routes.js, scripts/migratePortfolioV2.js

Each had its own near-identical regex chain — a real risk of silent behavioral drift between features. Consolidated into server/utils/slugify.js; live-verified the portfolio API still works correctly after the refactor.

MediumFixed & VerifiedRef-read-during-render bug in the login form's disabled-state logic
client/src/pages/Login.jsx

A useRef mutation was read directly in the render body to compute the submit button's disabled state — ref mutations don't trigger re-renders, so the UI could show a stale enabled/disabled state for a tick. Converted to real useState; confirmed via ESLint that this class of violation is now clear in this file.

MediumFixed & Verified7 confirmed orphaned/dead component files
AnimatedBackground.jsx, FeatureGate.jsx, FileUpload.jsx, ImageRequiredCard.jsx, LiquidButton.jsx, NotificationBell.jsx, PlanBadge.jsx

Independently re-verified (not just trusted from the research pass) that zero other files reference any of these seven components. Deleted all seven; confirmed a clean production build afterward with no broken imports.

LowFixed & VerifiedNeither package.json pinned a Node engine version
client/package.json, server/package.json

Combined with bleeding-edge majors already in use (Express 5, Mongoose 9, React 19), an untested Node version on a fresh production install had no early warning. Added "engines": {"node": ">=20.0.0"} to both.

Already solid — verified, not re-litigated

  • The centralized error-handling middleware is genuinely well-built: correctly differentiates dev/prod detail, maps every common Mongoose/JWT error type to the right status code.
  • Compression and Helmet (with a real CSP, not disabled) are both correctly applied.
  • Every process.env.* referenced in the server, and every import.meta.env.VITE_* referenced in the client, is documented in the corresponding .env.example file — no undocumented required config.
  • The SPA-fallback / split-domain deploy architecture (static frontend + reverse-proxied API) is coherent and correctly configured in nginx, aside from the syntax error above.
  • Zero stray console.log/debugger statements in client production code.

Documented, not force-fixed this session

  • Medium — Two parallel toast/notification systems in the client (a custom Toast.jsx globally, react-hot-toast directly in 15 other files). A real consolidation opportunity, but not something to refactor blind across 15 files without dedicated test coverage this late in a launch cycle.
  • Medium — 143 ESLint issues remain (mostly no-unused-vars, no-empty swallowed catches, react-hooks/exhaustive-deps warnings) — real housekeeping debt, not correctness bugs, aside from the one fixed above.
  • Low — Several very large single-component files (AIChatWidget.jsx 1,610 lines, AdminSupportAI.jsx 1,309, ProjectRequestForm.jsx 1,259, HeroDemo.jsx 1,092) — maintainability concerns worth splitting eventually, not bugs.
  • Low — No structured logging (winston/pino) in the server; ad-hoc console.log for Stripe webhook events, captured by PM2 but unstructured/ungraded.
  • Low — No production sourcemaps configured, so a future error-tracking tool (Sentry etc.) couldn't symbolicate stack traces — not a blocker since none is wired in yet.
  • 7 pre-existing, stale test assertions in the Jest suite reference route code from an earlier architecture version that no longer exists (e.g. a /image/:id route, a "stream error handler" pattern) — confirmed unrelated to any change made in this audit; recommend pruning or rewriting these tests rather than resurrecting dead code paths to satisfy them.

09Recommendations by Priority

Critical (address before or immediately after launch)

  • None outstanding. Both Critical findings from this audit (the message-thread IDOR and the nginx config syntax error) were fixed during this engagement.

High

  • Server-side rendering or prerendering. The single biggest lever left for SEO and social-sharing quality. A pragmatic first step: a prerendering plugin (e.g. vite-plugin-ssr-style or a headless-Chrome prerender step at build time) for the public marketing routes only (Home, Portfolio, Case Studies, Blog) — the authenticated app shell doesn't need it.
  • Dependency security upgrade pass. 13 high-severity npm advisories (multer, mongoose, nodemailer, axios, ws, engine.io) all require breaking major-version bumps. Schedule a dedicated sprint with full regression testing — do not force-upgrade during a launch week.

Medium

  • Consolidate the two parallel toast/notification systems onto react-hot-toast (already the more widely used of the two).
  • Work down the remaining 143 ESLint issues, prioritizing the react-hooks/exhaustive-deps and react-hooks/set-state-in-effect warnings (stale-closure/cascading-render risk) over the cosmetic no-unused-vars/no-empty ones.
  • Replace the naive regex-based XSS sanitizer and NoSQL-key stripper with a maintained library (e.g. sanitize-html) for genuine defense-in-depth rather than a best-effort pattern match.
  • Split the largest single-component files (AIChatWidget.jsx, AdminSupportAI.jsx, ProjectRequestForm.jsx, HeroDemo.jsx) — all 1,000+ lines — into smaller, independently-testable pieces.
  • Prune or rewrite the 7 stale Jest assertions referencing a pre-"Schema v2" route architecture that no longer exists.
